## ВВЕДЕНИЕ

В современной индустрии общественного питания (HoReCa) эффективное управление бронированием столиков является критически важным бизнес-процессом. По данным отраслевых исследований, рестораны теряют до 20% потенциальной выручки из-за неэффективного управления посадочными местами: двойные бронирования, неявки гостей, отсутствие оперативной информации о свободных столиках в реальном времени.

Цифровизация процесса бронирования позволяет решить эти проблемы, предоставляя как гостям удобный интерфейс для выбора столика, так и администрации ресторана — инструменты для управления загрузкой зала. Мобильные приложения для бронирования столиков становятся стандартом отрасли, а наличие качественного бэкенд-сервиса с открытым API является необходимым условием для их функционирования.

Актуальность данной работы обусловлена растущим спросом на автоматизацию процессов в сфере HoReCa, необходимостью интеграции с картографическими сервисами для навигации к ресторану и потребностью в визуализации карты зала для удобного выбора столика гостем.

**Цель работы** — разработка REST API сервиса для бронирования столиков в ресторанах с поддержкой визуализации карты зала, проверки доступности в реальном времени, системы email-уведомлений и интеграции с картографическими сервисами.

**Задачи:**

1. Провести анализ предметной области и существующих решений для бронирования столиков
2. Спроектировать архитектуру приложения с использованием слоистого подхода
3. Реализовать REST API с полным CRUD для ресторанов, столиков и бронирований
4. Реализовать систему аутентификации и авторизации на основе JWT
5. Реализовать механизм проверки пересечений бронирований по времени
6. Реализовать систему email-уведомлений о статусе бронирования
7. Обеспечить контейнеризацию приложения (Docker, Docker Compose)
8. Обеспечить качество кода через модульное тестирование (coverage ≥ 90%)
9. Настроить CI/CD pipeline с SAST-анализом и проверкой зависимостей

## 1 АНАЛИТИЧЕСКАЯ ЧАСТЬ

### 1.1 Описание предметной области

Предметная область данного проекта — автоматизация процесса бронирования столиков в ресторанах (сегмент HoReCa — Hotel, Restaurant, Catering).

**Основные сущности предметной области:**

**Ресторан** — заведение общественного питания с определённым количеством посадочных мест, расположением, типом кухни и графиком работы. Каждый ресторан имеет уникальный адрес и геокоординаты для интеграции с картографическими сервисами (Яндекс.Карты, Google Maps).

**Зал (Floor Plan)** — физическое пространство ресторана с расположением столиков. Зал характеризуется размерами (ширина и высота в пикселях для визуализации на экране мобильного устройства) и разделён на зоны: основной зал (main), терраса (terrace), VIP-зона (vip), барная зона (bar).

**Столик** — единица посадочного места с определённой вместимостью (от 1 до 20 человек), формой (круглый, квадратный, прямоугольный) и координатами расположения на карте зала. Форма и координаты используются для визуализации в мобильном приложении.

**Бронирование** — резервирование конкретного столика на определённую дату, время и продолжительность для указанного количества гостей. Бронирование проходит через жизненный цикл статусов:
- `pending` (ожидает подтверждения) — начальный статус после создания
- `confirmed` (подтверждено) — администратор подтвердил бронирование
- `completed` (завершено) — визит состоялся
- `cancelled` (отменено) — отменено гостем или администратором

**Пользователь** — гость ресторана или администратор системы. Гость может просматривать рестораны, бронировать столики и управлять своими бронированиями. Администратор дополнительно управляет ресторанами, столиками и подтверждает бронирования.

**Бизнес-процесс бронирования включает следующие этапы:**

1. Гость выбирает ресторан по критериям (тип кухни, расположение, средний чек)
2. Гость просматривает карту зала и видит свободные/занятые столики на нужную дату
3. Гость выбирает столик и указывает время, продолжительность и количество гостей
4. Система проверяет доступность (отсутствие пересечений с существующими бронированиями)
5. Создаётся бронирование со статусом «ожидает подтверждения»
6. Администратор подтверждает бронирование
7. Гость получает email-уведомление о подтверждении
8. По завершении визита бронирование переводится в статус «завершено»

### 1.2 Обзор существующих аналогов

В ходе анализа были рассмотрены следующие существующие решения:

**OpenTable** — крупнейшая мировая платформа бронирования ресторанов (основана в 1998 году, более 60 000 ресторанов). Достоинства: огромная база ресторанов, интеграция с POS-системами, рейтинги и отзывы, мобильные приложения. Недостатки: закрытый API, высокая стоимость подключения для ресторанов (от $249/мес), ориентация на рынок США и Западной Европы, невозможность self-hosted развёртывания.

**Яндекс.Еда (раздел бронирования)** — интеграция с экосистемой Яндекса, использование Яндекс.Карт для навигации, знакомый интерфейс для российских пользователей. Недостатки: ограниченный функционал бронирования (только выбор времени и количества гостей), отсутствие визуализации карты зала, невозможность выбора конкретного столика, зависимость от экосистемы Яндекса.

**Resy** — современная платформа с фокусом на премиальные рестораны (приобретена American Express в 2019). Достоинства: управление очередью (waitlist), аналитика загрузки, интеграция с Apple Wallet. Недостатки: только SaaS-модель, нет возможности self-hosted развёртывания, высокая стоимость, ориентация на премиум-сегмент.

**TableIn** — европейская система с визуализацией зала и управлением сменами. Достоинства: drag-and-drop редактор зала, управление сменами персонала, SMS-уведомления. Недостатки: устаревший технологический стек (PHP/jQuery), отсутствие мобильного API, медленная работа при большом количестве бронирований.

**Сравнительная таблица:**

| Критерий | OpenTable | Яндекс | Resy | TableIn | Наше решение |
|----------|-----------|--------|------|---------|--------------|
| Открытый API | ✗ | ✗ | ✗ | ✗ | ✓ |
| Карта зала | ✗ | ✗ | ✗ | ✓ | ✓ |
| Self-hosted | ✗ | ✗ | ✗ | ✓ | ✓ |
| Геонавигация | ✓ | ✓ | ✗ | ✗ | ✓ |
| Email-уведомления | ✓ | ✓ | ✓ | ✓ | ✓ |
| Проверка пересечений | ✓ | ✓ | ✓ | ✓ | ✓ |
| Docker | ✗ | ✗ | ✗ | ✗ | ✓ |

**Выводы из анализа:** большинство решений являются закрытыми SaaS-платформами без возможности self-hosted развёртывания и без открытого API. Разрабатываемая система отличается: открытым REST API для интеграции с любыми мобильными приложениями; визуализацией карты зала с реальными координатами столиков; возможностью развёртывания на собственной инфраструктуре; контейнеризацией для простого масштабирования.

## 2 ПРОЕКТНАЯ ЧАСТЬ

### 2.1 Архитектура приложения

Для реализации системы выбрана слоистая (layered) архитектура, обеспечивающая чёткое разделение ответственности и независимую тестируемость каждого компонента.

**Слои приложения:**

1. **API Layer (Presentation)** — FastAPI-роутеры, обработка HTTP-запросов, валидация входных данных через Pydantic-схемы, dependency injection для аутентификации. Этот слой не содержит бизнес-логики и отвечает только за преобразование HTTP ↔ DTO.

2. **Service Layer (Business Logic)** — сервисные классы, инкапсулирующие всю бизнес-логику: проверка пересечений бронирований, валидация бизнес-правил (вместимость, дата в будущем), оркестрация операций с несколькими сущностями.

3. **Data Layer (Persistence)** — SQLAlchemy ORM модели с декларативным маппингом, асинхронное взаимодействие с PostgreSQL через asyncpg-драйвер.

4. **Infrastructure Layer** — конфигурация приложения (pydantic-settings), модуль безопасности (JWT, bcrypt), email-уведомления (aiosmtplib), подключение к Redis.

Взаимодействие между слоями осуществляется строго сверху вниз: API → Service → Data. Каждый слой зависит только от нижележащего, что обеспечивает возможность замены реализации (например, замена PostgreSQL на другую СУБД) без изменения верхних слоёв.

**Контейнерная архитектура (Docker Compose):**

| Сервис | Образ | Назначение | Порт |
|--------|-------|-----------|------|
| app | python:3.12-slim | FastAPI-приложение | 8000 |
| db | postgres:16-alpine | Хранение данных | 5432 |
| redis | redis:7-alpine | Кэширование | 6379 |
| mailhog | mailhog/mailhog | SMTP для разработки | 1025, 8025 |

## 3 ТЕХНОЛОГИЧЕСКАЯ ЧАСТЬ

### 3.1 Обоснование выбора языка программирования

Для реализации проекта выбран язык **Python версии 3.12+**. Обоснование выбора:

1. **Зрелая экосистема для веб-разработки** — наличие высокопроизводительных асинхронных фреймворков (FastAPI, Starlette), ORM (SQLAlchemy), инструментов тестирования (pytest).

2. **Нативная асинхронность** — поддержка async/await для неблокирующего I/O, что критично для работы с базой данных и сетевыми вызовами (SMTP, Redis) в высоконагруженном сервисе.

3. **Строгая типизация** — поддержка type hints (PEP 484) и Pydantic V2 для валидации данных на этапе выполнения, что снижает количество runtime-ошибок.

4. **Соответствие требованиям** — Python указан в методических указаниях как основной язык для бэкенд-разработки с ключевыми технологиями FastAPI и Pydantic V2.

### 4.2 Модели данных

Модели реализованы с использованием SQLAlchemy 2.0 Declarative Mapping с типизированными полями (Mapped[T]).

Пример модели Booking (фрагмент):

```python
class BookingStatus(enum.StrEnum):
    PENDING = "pending"
    CONFIRMED = "confirmed"
    CANCELLED = "cancelled"
    COMPLETED = "completed"

class Booking(Base):
    __tablename__ = "bookings"

    id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    user_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("users.id", ondelete="CASCADE"))
    table_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("tables.id", ondelete="CASCADE"))
    booking_date: Mapped[datetime] = mapped_column(DateTime(timezone=True), nullable=False)
    duration_minutes: Mapped[int] = mapped_column(Integer, default=120)
    guests_count: Mapped[int] = mapped_column(Integer, nullable=False)
    status: Mapped[BookingStatus] = mapped_column(Enum(BookingStatus), default=BookingStatus.PENDING)
```

### 4.3 Сервисный слой

Каждый сервис принимает AsyncSession через конструктор и инкапсулирует бизнес-логику. Пример проверки пересечений бронирований:

```python
async def _check_overlap(self, table_id: uuid.UUID, date: datetime, duration: int) -> bool:
    end_time = date + timedelta(minutes=duration)
    result = await self.session.execute(
        select(Booking).where(
            and_(
                Booking.table_id == table_id,
                Booking.status.in_([BookingStatus.PENDING, BookingStatus.CONFIRMED]),
                Booking.booking_date < end_time,
            )
        )
    )
    bookings = result.scalars().all()
    for booking in bookings:
        booking_end = booking.booking_date + timedelta(minutes=booking.duration_minutes)
        if booking_end > date:
            return True
    return False
```

### 4.5 Аутентификация и авторизация

Система использует JWT (JSON Web Tokens) с алгоритмом HS256. Пароли хешируются bcrypt с автоматической солью. Реализовано два уровня доступа:

- **User** — может бронировать столики, просматривать свои бронирования, отменять их
- **Admin** — дополнительно может управлять ресторанами, столиками, подтверждать бронирования

Dependency Injection обеспечивает проверку токена на уровне роутера:

```python
async def get_current_user(authorization: str | None = Header(None), session = Depends(get_session)) -> User:
    # Извлечение и валидация JWT, получение пользователя из БД
```

### 4.6 Система уведомлений

NotificationService отправляет email-уведомления через SMTP при:
- Подтверждении бронирования администратором
- Отмене бронирования

В development-окружении используется MailHog (порт 8025 — веб-интерфейс для просмотра писем). В production подключается реальный SMTP-сервер через переменные окружения.

### 4.7 Карта зала

Эндпоинт `/api/v1/tables/floor-plan/{restaurant_id}` возвращает JSON с:
- Размерами зала (width, height) для отрисовки canvas/SVG
- Массивом столиков с координатами (position_x, position_y), формой, зоной
- Флагом доступности (is_available) на указанную дату

Это позволяет мобильному приложению отрисовать интерактивную карту зала с возможностью выбора конкретного столика.

Статический анализ безопасности выполняется инструментом Bandit при каждом push в CI/CD pipeline. Конфигурация исключает тестовые файлы и assert-проверки (B101).

### Проверка зависимостей (Safety)

Инструмент Safety проверяет все зависимости из requirements.txt на наличие известных CVE-уязвимостей. Выполняется автоматически в CI.

### Безопасность на уровне приложения

1. **Хеширование паролей** — bcrypt с автоматической солью (cost factor 12)
2. **JWT с ограниченным временем жизни** — 30 минут по умолчанию
3. **Валидация входных данных** — Pydantic V2 с ограничениями (min_length, max_length, ge, le, regex patterns)
4. **SQL Injection** — защита через ORM (параметризованные запросы SQLAlchemy)
5. **CORS** — настраиваемая политика Cross-Origin Resource Sharing
6. **Каскадное удаление** — ON DELETE CASCADE предотвращает orphan-записи
7. **Разделение ролей** — admin/user с проверкой на уровне DI
